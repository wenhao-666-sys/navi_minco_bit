# 可逐步骤实现的双雷达外参标定

更新日期：2026-10-04  
适用项目：`navi_minco_bit`  
实践平台：Ubuntu 22.04 / ROS 2 Humble / NUC / 双 MID-360 / 双网口直连。  
核对源码基线：`6dba3a53bf20848ac92dc1fb0fdfdaf9e8376a44`。配置结论同时以本地实际工作区为准。

本文保存本次教学确认的九步执行顺序，并补充配置位置、操作示例和验收清单。**本文件是待执行的操作指南；编译、PTP、采集、标定和实车效果尚未在 NUC 上验证。所有复选框初始均为未完成。**

## 一、执行顺序和标定边界

```text
软件可运行
    ↓
固定安装、确认前后身份、测量粗略外参
    ↓
两个网口及驱动网络配置正常
    ↓
两台雷达的 PTP 同步正常
    ↓
关闭融合，确认四路原始数据
    ↓
准备标定配置，采集静止与运动 bag
    ↓
离线标定，检查统计与点云对齐结果
    ↓
将通过验收的外参写入驱动，恢复融合
    ↓
核对底盘坐标和主 IMU，验证 Point-LIO
```

每一步通过验收后再进入下一步。出现问题时，先回到对应步骤检查。

| 要确认的关系 | 用途 | `dual_lidar_calibration` 的职责 |
|---|---|---|
| 后雷达 → 前雷达 | 将两台雷达的点云融合到同一坐标系 | 求解这组刚体外参 |
| 主雷达 → 主 IMU | Point-LIO 的点云与 IMU 估计 | 不求解；需要核对设备坐标定义和配置 |
| 传感器 → 底盘参考点 | 确定底盘参考点的位置、朝向与安装高度 | 不求解 |
| 两台雷达及其 IMU 的时间关系 | 使用同一时基下的测量 | 使用时间戳配对；不建立 PTP、不估计时钟偏差 |
| `map → camera_init` | 将局部里程计对齐到先验地图 | 由导航中的 GICP 重定位负责，与安装外参标定分开 |

双雷达标定成功后，仍要完成底盘坐标核对和里程计验收。

**三个位置必须分清：**

1. `initial_extrinsic` 在标定配置中，是粗测初值。
2. 输出的 `extrinsic.yaml` 保存求解结果，不会自动修改驱动。
3. `merge_extrinsic_back_to_front` 在驱动参数中，是正式融合使用的外参。

## 四、逐步骤执行

### 步骤 1：准备 NUC 软件环境，让驱动和标定包可运行

先完成 ROS 2 Humble、Livox SDK2 和依赖安装，以及工作空间编译。至少让 `livox_ros_driver2` 与 `dual_lidar_calibration` 可用；第 9 步还需要 `point_lio`。

详细安装和编译说明见[导航使用手册第 04—05 章](manual/NAVI_MINCO_BIT_USER_MANUAL.md)。本次整理文档没有执行构建。

编译完成后，在 NUC 新终端中检查。`NAVI_WS` 改成实际仓库根目录：

```bash
source /opt/ros/humble/setup.bash
NAVI_WS="$HOME/navi_minco_bit"
cd "$NAVI_WS"
source "$NAVI_WS/install/setup.bash"
ros2 pkg prefix livox_ros_driver2
ros2 pkg executables livox_ros_driver2
ros2 pkg executables dual_lidar_calibration
```

每次打开用于驱动、录包、标定或 Point-LIO 的新终端，都要加载 ROS 和这个工作空间环境。没有 `install/setup.bash` 时，应先完成环境与构建，不继续运行后面的命令。

**验收：**

- [ ] 驱动来自当前导航工作空间。
- [ ] 能找到 `livox_ros_driver2_node`。
- [ ] 能找到标定可执行程序 `calibrate`。
- [ ] 已记录源码版本、ROS 版本和 SDK2 版本。

若出现 `Package not found` 或可执行程序不存在，先检查构建与环境加载。

### 步骤 2：固定安装，确认前后雷达，测量粗略外参

本教程将前雷达作为 main，后雷达作为 secondary。确认两台设备的序列号与 IP，记录它们实际坐标轴方向。

测量后雷达相对前雷达的大致平移和旋转，记录为 `[x, y, z, roll, pitch, yaw]`。前三项单位为米，后三项为弧度。还要单独记录主传感器相对底盘参考点的关系。

外参约定是：

```text
p_front = R_back_to_front × p_back + t_back_to_front
```

`t_back_to_front` 是后雷达原点在前雷达坐标系中的位置。这组外参表示两台设备的相对安装关系，不是机器人在地图中的初始位置。

采集时两台雷达应作为一个刚性组件一起运动，不能分别转动后再沿用同一组外参。机械关系变化后重新采集和标定。

**验收：**

- [ ] 前后身份、序列号和 IP 对应明确。
- [ ] 安装关系稳定，有粗测平移和旋转值。
- [ ] 测量方向是后雷达到前雷达。
- [ ] 底盘参考点的位置、朝向和安装高度单独留档。

### 步骤 3：配置两个网口，打通两台雷达

接线：

```text
前 MID-360 → 网线 → NUC 网口 1
后 MID-360 → 网线 → NUC 网口 2
```

雷达由供电线供电。查看实际接口与路由：

```bash
ip -br link
ip -br addr
ip route
```

分别配置主机与雷达地址。两条独立链路可选不同网段以简化路由；若保留同一网段，需要处理每台雷达的出接口、源地址和 ARP，不能仅给两个网口设置不同 IP 后就认为完成。

修改驱动实际读取的 JSON，让每台雷达对应正确的主机接收接口。**仓库当前 JSON 将接收地址统一设为 `192.168.1.47`；双网口方案需结合实际 SDK2 版本适配，不能直接照抄这一单接收地址布局。**参考[SDK2 网络配置说明](https://github.com/Livox-SDK/Livox-SDK2#4-config-file)。

修改 JSON 中的雷达地址并不会自动修改雷达本机 IP。主机接收 IP 与雷达自身 IP 也不是同一项。

**验收：**

- [ ] 两台雷达各自的物理链路正常。
- [ ] IP、掩码、路由与实际接线一致。
- [ ] 驱动接收地址确实属于相应主机接口。
- [ ] 驱动能持续接收两台雷达的点云与 IMU。

`ping` 是辅助检查；点云和 IMU 持续有效才证明数据链可用。

### 步骤 4：建立并验证 PTP 时间同步

在采标定数据前，让两台雷达及其 IMU 使用同一时间基准。双网口方案需要覆盖两个接口，并核对各接口的时间戳能力。

当前 `ptp_sync.bash` 只绑定 `enp86s0`，而且包含 `killall -9 ptp4l phc2sys`。不能简单运行两份原脚本；第二份可能终止第一份的进程。应根据实际接口和时钟能力采用适配后的同步方案。

不能仅以“PTP 进程存在”作为成功证据。结合 Livox Viewer 的同步类型、PTP 日志以及四路消息的时间戳检查实际同步状态。参考[Livox 官方时间同步说明](https://github.com/Livox-SDK/livox_wiki_en/blob/master/source/tutorials/new_product/common/time_sync.rst)。

**验收：**

- [ ] 两台雷达实际使用预期的 PTP 同步方式。
- [ ] 时间戳持续递增，没有明显跳变或回退。
- [ ] 两台雷达的时间处于同一基准。
- [ ] 每台 IMU 的数据覆盖对应点云的采样时间区间。
- [ ] 同步状态和时间检查证据已保存。

`sync_tolerance_ms: 5.0` 只是标定工具配对帧的时间窗口，不是时钟偏差校准，也不是“PTP 精度已达到 5 ms”的证明。

### 步骤 5：关闭融合，确认四路原始数据

为避免独立 launch 和组件 YAML 的参数来源混用，本文标定阶段采用：**单独运行驱动可执行程序，并显式传入自己的采集 YAML。**

在仓库根目录准备副本：

```bash
mkdir -p "$HOME/navi_config" "$HOME/bags"
cp src/perception/livox_ros_driver2/config/mixed_MID360_component.yaml \
  "$HOME/navi_config/livox_calibration.yaml"
cp src/perception/livox_ros_driver2/config/mixed_MID360_config.json \
  "$HOME/navi_config/mixed_MID360_config.json"
```

在 JSON 副本中写入第 3 步验收的真实网络配置。在 `~/navi_config/livox_calibration.yaml` 的 `ros__parameters` 内设置：

```yaml
xfer_format: 1
multi_topic: 1
enable_internal_lidar_merge: false
```

同时将 `user_config_path` 写成该 JSON 副本的**实际绝对路径**，例如 `/home/你的实际用户名/navi_config/mixed_MID360_config.json`。这里的用户名示意必须替换；不要填字面量 `~` 或保留 `$(find-pkg-share ...)`。直接用 `--params-file` 启动时，不会替你执行 launch 的路径替换。

环境加载完成后启动：

```bash
ros2 run livox_ros_driver2 livox_ros_driver2_node --ros-args \
  -r __node:=livox_calibration_driver \
  --params-file "$HOME/navi_config/livox_calibration.yaml"
```

在另一个已加载相同环境的终端检查：

```bash
ros2 param get /livox_calibration_driver enable_internal_lidar_merge
ros2 param get /livox_calibration_driver multi_topic
ros2 param get /livox_calibration_driver user_config_path
ros2 topic list -t
```

按仓库原 IP，话题示例为：

| 角色 | 示例话题 | 预期消息类型 |
|---|---|---|
| 前雷达原始点云 | `/livox/lidar_192_168_1_135` | `livox_ros_driver2/msg/CustomMsg` |
| 前雷达 IMU | `/livox/imu_192_168_1_135` | `sensor_msgs/msg/Imu` |
| 后雷达原始点云 | `/livox/lidar_192_168_1_122` | `livox_ros_driver2/msg/CustomMsg` |
| 后雷达 IMU | `/livox/imu_192_168_1_122` | `sensor_msgs/msg/Imu` |

例如后雷达实际 IP 改为 `192.168.2.122`，应重新查看实际话题，再同步修改录包和标定配置。不要继续盲用表中的 `.1.122`。

**验收：**

- [ ] 融合参数为 `false`，`multi_topic` 为 `1`。
- [ ] 读取的是已验收的 JSON 副本。
- [ ] 四路原始数据都存在，频率与内容正常。
- [ ] 两路点云都是未融合的 `CustomMsg`。

采集阶段只需要驱动、同步和录包，不需要启动 GICP、导航或底盘控制。开启融合后的 `/livox/lidar` 不能替代两路原始点云来重新求外参。

### 步骤 6：准备标定配置，采静止与运动 bag

在仓库根目录复制模板：

```bash
cp src/perception/dual_lidar_calibration/config/example.yaml \
  "$HOME/calibration.yaml"
```

修改 `~/calibration.yaml` 中四个话题为第 5 步实际看到的名称；把 `initial_extrinsic` 换成第 2 步的粗测数值。模板中的 `[0.0, 0.4, 0.0, -0.35453, 0.0, 0.0]` 是已有布局示例，不是你的设备测量结果。

```yaml
# 示例话题，执行前按实际设备核对
main_lidar_topic: /livox/lidar_192_168_1_135
main_imu_topic: /livox/imu_192_168_1_135
secondary_lidar_topic: /livox/lidar_192_168_1_122
secondary_imu_topic: /livox/imu_192_168_1_122

# 后雷达 → 前雷达，前三项米、后三项弧度；替换为实际粗测值
initial_extrinsic: [0.0, 0.4, 0.0, -0.35453, 0.0, 0.0]
```

设备内置 LiDAR—IMU 坐标关系还要核对 `main_lidar_to_imu_rpy` 和 `secondary_lidar_to_imu_rpy`。模板默认两者为零旋转；这些是输入假设，不是该工具自动标定出的结果。

优先录 MCAP，需要安装 Humble 的 MCAP 存储插件，并在录制终端加载当前工作空间的自定义消息。以下命令仅适用于话题与示例一致、输出目录尚不存在的情况；后续采集使用新的 bag 名称。

**先采静止 bag：**整个组件静止，可先采约 30—60 秒，然后按 Ctrl+C 正常结束录制。时长是起步建议，不是通过保证。

```bash
ros2 bag record -s mcap -o "$HOME/bags/dual_lidar_static" \
  /livox/imu_192_168_1_135 \
  /livox/imu_192_168_1_122
```

**再采运动 bag：**两台雷达一起缓慢、平稳运动，保持安装关系不变，录四路数据。场景应让两台雷达共同看到墙面、地面、柱子等不同方向结构，避免只观察一面大平墙。

```bash
ros2 bag record -s mcap -o "$HOME/bags/dual_lidar_motion" \
  /livox/lidar_192_168_1_135 \
  /livox/imu_192_168_1_135 \
  /livox/lidar_192_168_1_122 \
  /livox/imu_192_168_1_122
```

能够包含绕不同轴的旋转更好。若底盘只方便绕竖直轴转动，可以增加静止 bag 提供重力与偏置约束；围绕重力方向的旋转仍需初值与点云几何进一步约束。工具当前主要做旋转去畸变，采集时减少快速平移和剧烈运动。

按 Ctrl+C 正常结束后检查：

```bash
ros2 bag info "$HOME/bags/dual_lidar_static"
ros2 bag info "$HOME/bags/dual_lidar_motion"
```

**验收：**

- [ ] 标定配置的四个话题与实际 bag 完全一致。
- [ ] 粗测初值方向和单位正确。
- [ ] 静止 bag 中有两个 IMU 的有效数据。
- [ ] 运动 bag 中有两路原始点云及两路 IMU，数量合理。
- [ ] 运动时两雷达安装关系固定，有足够重叠结构。
- [ ] 采集日志和同步证据已留档。

### 步骤 7：离线标定，验收统计和对齐结果

停止录制后，标定程序直接读取 bag，不需要 `ros2 bag play`。每次选择新的输出目录，避免把旧的成功外参与新的失败统计混在一起。

```bash
ros2 run dual_lidar_calibration calibrate \
  --bag "$HOME/bags/dual_lidar_motion" \
  --static-bag "$HOME/bags/dual_lidar_static" \
  --config "$HOME/calibration.yaml" \
  --output "$HOME/calibration_results/dual_lidar_01"
echo $?
```

`--static-bag` 是可选项。如果运动数据已提供充分的多轴旋转，可以不传；单轴运动时可用它辅助。`echo $?` 要紧接标定命令，否则读到的可能是其他命令的退出码。

| 退出码 | 含义 | 下一步 |
|---|---|---|
| `0` | 通过工具的质量门槛 | 查看统计、人工检查点云，并用另一段数据复核 |
| `2` | 完成求解流程，但数据或结果未通过质量门槛 | 查看拒绝原因，检查数据、时间和初值后重试 |
| `1` | 输入、配置或运行错误 | 检查路径、话题、数据类型、依赖与错误日志 |

成功时的输出：

| 文件 | 检查内容 |
|---|---|
| `summary.yaml` | `success`、`quality`、接受帧数、IMU 可观测性、外参离散程度 |
| `frame_results.csv` | 每帧收敛情况、接受/拒绝原因、RMSE、重叠比例和外参 |
| `aligned_preview.pcd` | 主雷达红色点云与变换后副雷达青色点云的对齐情况 |
| `extrinsic.yaml` | 最终六参数与 `merge_extrinsic_back_to_front` |
| `extrinsic_matrix.txt` | 后雷达到前雷达的 4×4 变换 |

预览 PCD 展示一个接受帧对的对齐效果，不代表整段数据的全部表现。统计和独立数据复核需要一起看。默认质量门槛通过，也不自动证明达到你的车辆精度要求。

**验收：**

- [ ] 退出码为 `0`，`summary.yaml` 中 `success: true`、`quality: PASS`。
- [ ] 接受帧数、误差与外参波动符合要求。
- [ ] 结果的位置和角度与实际机械布局相符。
- [ ] 红/青点云在共同结构上对齐，无明显不合理错层。
- [ ] 用另一段数据复核，结果具有一致性。

失败时本次运行只写统计文件，不输出新的可用外参；如果目录里已经存在旧 `extrinsic.yaml`，不能把它当成本次结果。先检查 `summary.yaml` 和本次退出码。

### 步骤 8：写入正式驱动配置，恢复融合并验证

将采集参数复制成运行参数副本：

```bash
cp "$HOME/navi_config/livox_calibration.yaml" \
  "$HOME/navi_config/livox_runtime.yaml"
```

编辑 `~/navi_config/livox_runtime.yaml` 的 `ros__parameters`：

1. 将 `enable_internal_lidar_merge` 改为 `true`。
2. 将 `merge_front_ip`、`merge_back_ip` 改为真实前后雷达 IP。
3. 将本次成功结果的 `merge_extrinsic_back_to_front` 六个数值原样写入同名参数。
4. 保留已验收 JSON 的绝对路径。

只取结果文件中的六参数值，**不要把整个 `extrinsic.yaml` 当作 ROS 参数文件直接替换驱动 YAML**。结果文件还含有矩阵和统计描述，不是驱动参数文件的结构。

结束第 5 步的驱动进程，重新运行：

```bash
ros2 run livox_ros_driver2 livox_ros_driver2_node --ros-args \
  -r __node:=livox_runtime_driver \
  --params-file "$HOME/navi_config/livox_runtime.yaml"
```

另一个环境已加载的终端核对：

```bash
ros2 param get /livox_runtime_driver enable_internal_lidar_merge
ros2 param get /livox_runtime_driver merge_front_ip
ros2 param get /livox_runtime_driver merge_back_ip
ros2 param get /livox_runtime_driver merge_extrinsic_back_to_front
ros2 topic info /livox/lidar -v
ros2 topic hz /livox/lidar
```

结合融合调试输出或后续标准点云输出，检查静止、直行和转动时的表现。`CustomMsg` 不是通用 3D 面板默认可直接显示的标准点云，不能把“显示不了”直接当成融合失败。

**验收：**

- [ ] 新驱动进程加载的是运行副本，融合参数为 `true`。
- [ ] 前后身份、IP 与标定输入一致。
- [ ] 实际外参值与本次通过验收的结果一致。
- [ ] `/livox/lidar` 正常输出。
- [ ] 静止、直行和转动时，点云没有明显不合理错层或重影。

静止时就错层，先查外参、前后身份和变换方向；静止较好、转动重影时，进一步查同步、采样时间和畸变。这些是排查线索，仍需数据确认。

本文使用自定义运行副本，默认 `start.bash` 或混合 launch 不会自动采用它。以后使用默认启动脚本时，必须核对它实际加载的参数路径，将已验收配置接入那个入口。使用包安装目录读取配置时，也要确认安装副本与修改一致。

### 步骤 9：核对底盘坐标和主 IMU，验证 Point-LIO

先核对主雷达与主 IMU 的坐标关系及 Point-LIO 的 `mapping.extrinsic_T/R`。还要核对传感器到底盘参考点的位移和朝向。

当前 `laserMapping.cpp` 发布 `base_link` 时含原车辆的 `(0, 0.20, 0)` 偏移和特定姿态处理。它不是一套可直接套用到任意舵轮底盘的安装配置。双雷达标定不会修改这部分，需要依据实际机械布局适配和验收，不能通过另外发布同一子 frame 的 TF 来假定已有逻辑被自动替换。

结束第 8 步单独运行的驱动，避免重复控制雷达。完成相应配置核对后，使用能显式传参的通用组件 launch：

```bash
ros2 launch point_lio livox_pointlio_intra_process.launch.py \
  driver_params_file:="$HOME/navi_config/livox_runtime.yaml" \
  pointlio_imu_topic:=/livox/imu_192_168_1_135
```

这里的 IMU 话题仍是原 IP 示例，改成真实主雷达话题。该 launch 会将 `pointlio_imu_topic` 覆盖到 Point-LIO 的 `common.imu_topic`；只改 `mid360.yaml` 不能保证实际订阅跟着改变。

先做静止、直行和旋转检查，观察里程计、标准配准点云和 TF。通过后再进入建图、GICP 重定位和导航。

**验收：**

- [ ] 当前只运行一套雷达驱动。
- [ ] Point-LIO 订阅的是融合点云和实际主雷达 IMU。
- [ ] 雷达—IMU 与传感器—底盘关系符合设备实际。
- [ ] 静止时位姿稳定，直行和旋转时方向与运动一致。
- [ ] TF、标准点云和里程计时间关系合理。
- [ ] 对你的舵轮底盘完成坐标验收后，才进入导航控制接入。
